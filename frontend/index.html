IA vs Stack Overflow : la fin du copier-coller ou le début d'une nouvelle dépendance ?

14 mai 2025 5 min de lecture IA & Dev

Depuis que les LLMs sont devenus accessibles à tous, la manière dont les développeurs résolvent leurs problèmes a changé. Stack Overflow accusait déjà une baisse de trafic significative avant l'arrivée massive de ChatGPT — depuis, c'est une tendance confirmée.

Ce qu'on a gagné

La réponse instantanée. Fini d'éplucher dix fils de discussion pour trouver la seule réponse qui correspond exactement à ta version de Node ou ta config Webpack. Tu décris ton problème en langage naturel, tu obtiens une réponse contextualisée.

Pour un dev qui débute, c'est révolutionnaire. Pour un dev confirmé, c'est un gain de temps massif sur les tâches répétitives — écrire un test unitaire, générer un type TypeScript depuis un objet, transformer un tableau de données.

Ce qu'on a peut-être perdu

Le débogage actif. Quand tu cherchais sur SO, tu lisais les mauvaises réponses aussi. Tu comprenais pourquoi ça ne marchait pas dans certains cas. Avec l'IA, on accepte souvent la première réponse plausible sans vraiment tester les cas limites.

La réponse en copy-paste a changé de forme — elle est maintenant plus longue, mieux présentée, mais le risque de comprendre superficiellement reste le même.

Mon approche

J'utilise l'IA comme un pair programmer, pas comme un moteur de recherche. Je lui explique mon contexte complet, je lis le code généré ligne par ligne, et je teste chaque cas. La différence n'est pas dans l'outil — elle est dans l'intention.

ORM et relations : OneToMany, ManyToMany — quand ça casse et pourquoi

2 avr. 20257 min de lectureBackend

Les ORM simplifient l'accès aux données, mais les relations entre entités restent une source classique de bugs. Voici ce que j'ai appris en travaillant avec Prisma et TypeORM.

Le cas OneToMany

Le problème le plus courant : oublier le côté "Many" de la relation. Dans Prisma, une relation User → Posts requiert à la fois le champ posts Post[] sur User ET le champ userId + user User sur Post.

model User {
  id    Int    @id @default(autoincrement())
  posts Post[]
}

model Post {
  id     Int  @id @default(autoincrement())
  userId Int
  user   User @relation(fields: [userId], references: [id])
}

Le cas ManyToMany

Avec une table de jointure implicite, Prisma gère tout. Mais dès qu'on a des données sur la relation (ex: une date d'ajout), il faut une table explicite. C'est là que les débutants se perdent.

Déployer une app Next.js avec Docker et GitHub Actions

18 fév. 202510 min de lectureDevOps

Vercel est excellent, mais comprendre le déploiement manuel te donne un contrôle total et te prépare aux environnements d'entreprise. Voici comment j'ai mis en place ma pipeline.

Le Dockerfile

FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY --from=builder /app/.next ./.next
COPY --from=builder /app/node_modules ./node_modules
CMD ["node", "server.js"]

GitHub Actions

Le workflow se déclenche sur chaque push sur main, build l'image Docker, la push sur le registry, puis redémarre le container sur le serveur via SSH.

KONDUI CI : construire un produit pour un marché informel

3 jan. 20258 min de lectureProduit

Quand j'ai commencé à concevoir KONDUI CI, j'avais en tête un modèle simple : mettre en relation des chauffeurs et des employeurs. La réalité du marché ivoirien m'a rapidement rappelé à l'ordre.

Le vrai problème à résoudre

La confiance. Dans un marché où 70% des transactions se font de bouche à oreille, un profil en ligne ne suffit pas. Il a fallu réfléchir à des mécanismes de vérification d'identité, de notation mutuelle, et d'escrow pour les paiements.

Adapter le produit au contexte

L'interface mobile-first n'était pas un choix esthétique — c'était une nécessité. 90% des utilisateurs cibles utilisent uniquement leur téléphone. Chaque fonctionnalité a été pensée pour fonctionner avec une connexion limitée et sur des appareils d'entrée de gamme.
